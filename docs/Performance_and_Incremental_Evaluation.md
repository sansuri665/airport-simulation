# 区域并行与玩家增量重算评估

## 1. 结论

区域/城市并行计算与玩家行动后的增量重算已经完成第一轮技术评估，但当前都**暂缓实施**。

这不是因为它们完全不可行，而是因为当前最重要的约束是：

- 固定 Seed 的结果必须保持完全一致。
- 随机数消费、浮点运算和输出排序不能因提速而变化。
- Windows 本地环境中的进程启动、模块导入和大对象传输可能抵消并行收益。
- 玩家经营和财务状态具有明显路径依赖，错误的增量起点会产生“看似合理但实际错误”的长期账本。

当前已经完成的缓存、按需加载、每 Run 锁和后台 Job 主要改善重复工作、页面首屏和等待体验；它们不宣称改变模型本身的计算速度。

## 2. 当前已经完成的低风险性能整理

在不改变模型数值的前提下，当前已完成：

- Viewer 按报告、区域和估值数据块按需加载。
- 配置 JSON 按文件状态缓存，并在变化后失效。
- 缓存列表只计算一次当前模型/配置指纹，再复用于各缓存项。
- 指纹依赖文件的字节内容按 `path + mtime_ns + size` 缓存，避免同一次服务生命周期反复读取未变化文件。
- 不同 Run 使用不同锁，同一 Run 的写入、玩家重算和缓存清理互斥。
- 可选后台 Run Job 让 HTTP 请求先返回 `jobId`，页面可以轮询状态；旧同步接口继续兼容。
- 无新玩家行动时，浏览器利用已加载的 `allQuarters` 前进或后退季度，不重复调用模型。

这些工作优先减少重复 IO、重复解析和不必要等待，风险低于改变模拟执行顺序。

## 3. 区域与城市并行评估

### 3.1 理论并行位置

全球主链完成后，14 个区域的区域宏观计算在结构上具有并行空间。区域对账完成后，各区域航空需求和航空供给也可以按区域分组。

城市机场市场在对应区域输入准备完成后，理论上可以按城市并行。当前中国大陆有 47 个城市市场，但只有北京继续进入完整季度经营、财务、估值和玩家闭环，因此“47 城市场并行”和“机场经营并行”不是同一件事。

### 3.2 确定性风险

并行实现必须同时保证：

- 每个任务使用独立、可复现的随机数对象或稳定 Seed 派生。
- 不共享可变模拟状态。
- 结果回到主进程后严格按 `REGION_ORDER`、城市 ID、Seed、年份和季度排序。
- CSV 字段顺序、JSON 序列化顺序和汇总遍历顺序保持不变。
- baseline、occurred 和 probabilistic 的固定 Seed 摘要与串行版本完全相同。

只比较最终总量不够；区域行、城市行、关键字段、表头和 Scenario 激活行也必须一致。

### 3.3 Windows 进程开销

模型计算以 Python 为主。线程对 CPU 密集计算可能受到 GIL 限制，因此真正并行通常需要多进程。

Windows 多进程使用 spawn 方式启动，子进程需要重新导入较大的模型模块，并在父子进程之间序列化全球、区域或城市行。对于 12 年短 Run，这些启动和传输成本可能高于计算本身；对于 60 年 Run，也需要实测才能确定收益。

过多 worker 还会增加：

- 内存峰值。
- 大列表复制。
- Windows 文件和进程调度压力。
- 测试环境与普通用户电脑之间的性能差异。

因此不能仅根据“有 14 区和 47 城”就默认并行一定更快。

### 3.4 如果未来实施

未来实验应满足：

1. 先只并行一个清晰边界，例如区域宏观，避免嵌套进程池。
2. worker 只返回内存结果，不直接写共享输出目录。
3. 父进程按固定顺序汇总、校验和写盘。
4. 同时测试 Windows 与 Linux、12 年与 60 年、1/2/4 worker。
5. 比较冷启动、热启动、总耗时、峰值内存和输出摘要。
6. 只有在固定 Seed 完全一致且普通 Windows 机器有稳定收益时才保留。

当前决定：技术上存在并行边界，但证据不足以证明收益稳定，暂不实施。

## 4. 玩家行动增量重算评估

### 4.1 当前行为

合同、项目或融资行动发生后，服务端根据完整行动日志重新生成玩家经营和财务路径。未变化的行动日志可以通过指纹复用已有模拟结果。

无新行动时，前端已经加载的 `allQuarters` 可以用于本地切换当前季度。这只优化页面推进，不是模型层增量重算，也不会产生新的经营结果。

### 4.2 为什么有路径依赖

理论上可以从“最早受影响季度”开始重算，但该季度的正确期初状态包含：

- 现金、应收应付和所有者权益。
- 固定资产原值、累计折旧、在建工程和残值底线。
- 每笔贷款余额、锁定利率、宽限期、付息和还本计划。
- 当年预缴税、年度汇算和税损结转队列。
- 合同周期、历史保底基准、已签条款和自动续约状态。
- 项目施工进度、资本开支、容量变化、投产和维护年龄。
- 航站楼名称、槽位状态、翻新与重建冷却期。
- 服务质量、商业乘数以及后续季度依赖的状态量。

缺少其中任何一项，后续季度都可能逐步偏离，而错误不一定立即报错。

### 4.3 真正增量重算需要什么

未来如果实施，需要先建立：

- 版本化、可校验的完整季度状态快照。
- 从快照恢复模型的正式接口。
- 合同、翻新、新建、拆除、重建和三类融资的组合回放测试。
- “全量重算”和“从季度 N 增量重算”的逐行等价测试。
- 配置或模型版本变化后自动废弃旧快照的规则。
- 行动删除、行动修改和同季度多种事务的明确排序规则。

维护这些状态快照本身也会增加 Schema、迁移和存储复杂度。当前北京单城模型的全量重算仍可接受，因此没有必要用高正确性风险换取尚未量化的收益。

当前决定：保留行动日志指纹缓存和无行动时的前端季度推进；玩家产生新行动后继续走服务端完整重算，增量模型实现暂缓。

## 5. 后台 Job 与模型并行不是一回事

当前可选接口：

```text
POST /api/run-job
GET  /api/jobs/<jobId>
```

后台 Job 的作用是让客户端不必在一个 HTTP 请求中一直等待。它使用有限 worker 执行完整 Run，并对同一个任务键去重。

它没有改变一个 Run 内部的全球、区域、城市计算顺序，因此不会自动缩短单个 Run 的模型耗时。旧的同步 `POST /api/run` 继续保留，已有页面和外部调用无需立即迁移。

## 6. 重新开启实施的条件

只有满足以下条件，才应重新考虑区域并行或玩家增量重算：

- 已有真实耗时数据证明模型计算而不是 Viewer、磁盘或重复缓存检查成为主要瓶颈。
- Windows 普通用户环境可以稳定复现收益。
- 60 年 baseline、occurred、probabilistic 和玩家行动回放覆盖足够。
- 串行与优化实现的输出能够逐行等价，而不只是汇总接近。
- 失败、取消、清理和并发写入不会留下半成品 Run 或损坏玩家存档。

在这些条件满足前，优先继续做低风险的按需加载、缓存复用、职责拆分、错误提示和测试保护。
