# 项目路线图

这份文档只保留尚未完成、仍有明确收益的工作。当前运行方式和数据边界由专题文档说明；已完成的 Release-only、Manifest v2、统一 Seed、宏观—利率修复、贷款利率 v0.3 和客流模型链 v0.4 由 Git 与正式专题文档保存，不在这里重复维护实施流水。当前数值模型为 `airport-model-v0.15`，输出协议为 `airport-model-output-v5`。

## 1. 下一步：资产层专项

只读审计已经确认，全球股票价格与含分红总回报共用一个状态，区域股票又缺少盈利锚，现存 Run 会出现区域 GDP 和航空需求长期增长而区域股票跌破起点的路径。该问题暂时不推翻宏观与客流主链，但在跨区域预测、正式估值和资产交易以前必须解决。

具体证据、会计口径、子 Goal 和测试设计见[资产层更新预研](Asset_Layer_Upgrade_PreResearch.md)。客流链已经完成数值、缓存和真实浏览器收口，本专项现在可以作为下一个独立 Goal；仍不得把资产公式变化与经营预测或城市扩展混在同一轮。

## 2. 随后：经营预测系统 v0.1

当前宏观、城市客流、季度经营、财务和贷款链已经能够提供一个稳定世界，但玩家仍缺少把客流判断转化为经营决策的中间层。下一阶段应先建立小范围、可解释的经营预测系统，不直接进入估值和交易。

建议先形成独立工作指导，再确定公式。首版至少需要：

1. 明确玩家预测的对象：客流、分项客流、容量利用、收入和主要成本，避免一次覆盖全部财务报表。
2. 区分真实世界结果、玩家可见历史、玩家假设和预测输出，预测不得直接读取隐藏未来。
3. 允许低、中、高三档预测投入或质量，并记录误差来源；首版不引入研究所、声誉或复杂情报网络。
4. 把预测结果接到合同、项目和融资的事前比较，但不自动替玩家决策。
5. 使用固定 Seed 比较预测与实际，建立方向、误差、稳定性和信息边界测试。

## 3. 随后：经营城市扩展

北京闭环稳定后，优先把完整经营能力扩展到中国区域，而不是立即增加全球城市。新增城市必须遵循[北京样板与新增完整经营城市指南](../reference/Beijing_Template_and_New_City_Guide.md)，逐一补齐设施、经营、合同、项目、财务和预测配置，不能只复制北京资产负债表。

建议先选择少量差异明显的样板城市，验证枢纽、旅游、区域门户等类型，再扩大覆盖。城市扩展不能改变同一 Seed 的全球和区域权威结果。

## 4. 中期：情报差、预期差与联合运行

经营预测能够稳定运行后，再让不同预测强度自然产生信息差和预期差。合同、项目和融资可以消费玩家确认的预测方案，但必须保留各模块独立结果和统一季度时点，避免形成无法解释的一键黑箱。

估值与交易系统排在这之后。只有经营预测、多个城市和联合运行形成可靠现金流与风险口径时，估值才具有可玩的决策意义。

## 5. 正式玩家信息边界

在把经营总览、预测、合同、项目、融资和季度推进合并为正式玩家流程前，需要先消除开发原型对真实未来的暴露。这项工作不改变模型公式，只改变玩家与审计接口能看到什么。

任务集群：

1. 盘点所有包含 `allQuarters`、未来合同结果、隐藏预测真值或事后评分的响应。
2. 正式玩家接口只返回当前季度可见历史、已购买报告和必要摘要；开发审计接口保持独立。
3. 明确预测报告的获取成本、按需加载、缓存和失效规则。
4. 决定独立预测页、候选实验室和开发审计入口在正式产品中的去留及权限。
5. 用固定 Seed、API Schema、玩家/审计双标签和真实浏览器验证信息边界，不改变模型结果。

这项工作暂不单独抢占经营预测开发，但在预测结果正式影响合同、项目或融资前必须完成。

## 6. 产品与模型方向

这些事项需要独立设计、参数和验收，不能混入机械重构：

- 为合同增加合作方、报价比较与谈判过程。
- 让项目方案、合同条款和融资条件在确认前按同一口径测算。
- 明确自营商业预算边界，并另行设计免税、奢侈品等销售预测。
- 让合同报价只使用玩家可见预测，不读取隐藏真实未来。
- 完善报告获取成本、质量和预测—实际对照机制。
- 重新定义估值的用途、输入和反馈后，再把它升级为正式系统。

涉及公式、参数、随机数消费或浮点顺序的变化必须升级模型版本，并建立新的固定 Seed 预期，不能以“重构”名义修改现有结果。

## 7. 按触发条件处理的维护项

以下事项有价值，但当前不单独发动大规模改造：

- 修改相关旧 GET 路由时补齐 `errorCode` 特征测试，再逐步统一错误格式。
- 只对审计确认仍会直接覆盖的权威单层输出补原子写入。
- 修改 `app.py` 或宏观编排器相关职责时顺手收敛内部兼容门面，不为减少转发层单独重写。
- 只有出现第三种稳定运行语义时才引入命名 Run Profile；当前 `full` 与 `seed-cache` 已足够。
- Viewer Release 在开发期间最多保留当前版和一个备份版，阶段验收后收敛到当前版。
- 只有 `output/` 再次明显增长时才重新测量重复；硬链接、内容寻址、SQLite、Parquet 或数据库必须由真实瓶颈触发。
- 正式 Run 保留策略等正式存档机制明确后再设计；任何自动清理都必须先有可预览计划和显式确认。

## 8. 明确暂缓

- 季度经营主函数拆分：风险高，当前没有功能需求支撑，不为降低行数而移动公式。
- 浏览器宏观场景模型重写：先决定它是非权威推演、数值等价实现还是服务端权威模型的客户端。
- 区域与城市并行：先证明计算是瓶颈，并保证跨平台随机数、浮点和汇总顺序一致。
- 玩家行动增量重算：先有版本化季度状态快照、恢复接口和全量/增量逐行等价测试。
- Brotli、数据库或 Parquet：现有 gzip、分块和保留策略不足时再评估。
- 研究所、资产交易、多人或 AI 对手：形成规则、数据边界和验收标准后再排期。

## 9. 共同完成标准

一个任务集群只有在以下条件都满足时才算完成：

- Python 3.13 完整测试通过，固定 Seed 数值没有无意变化。
- API、Schema、前端、缓存指纹和文档同步。
- Run、缓存、Viewer Release 和玩家存档边界没有混淆。
- 涉及 UI 时完成真实浏览器验收和信息可见性检查。
- 涉及输出清理时先生成只读计划，验证目标位于允许目录内，并记录可恢复性。
- 兼容入口有明确保留或退出结论。
- Roadmap 只记录未来事项；实施历史由提交和版本交接说明保存。
