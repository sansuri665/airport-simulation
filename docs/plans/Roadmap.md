# 项目路线图

这份文档只保留尚未完成且已有明确依据的方向。已经完成的迁移、瘦身和重构过程由 Git 保存，不再作为未来待办重复堆叠。

## 1. 当前基线

以下边界是当前路线图的起点：

- Python 3.13 是唯一支持版本；
- `airport_sim` 是统一命令和正式 8776 服务入口；
- 五个页面位于 `web/`，正式 URL 保持稳定；
- Run、缓存、Viewer 发布和玩家存档已经分离；
- 固定 Seed、60 年模型、API、Schema、原子发布和页面 DOM 已有自动化保护；
- 区域旅客承接量是参考估计，城市市场只继承区域运力、信心和约束信号，不把区域数量当作硬上限；
- 城市年度市场统一分配五类客群可承接供给，季度经营与预测读取同一权威结果；
- 中国大陆 47 城已经使用显式航司行为模板与经营周期，区分全球/国家/区域/次级门户及旅游、战略、高原特征；
- 北京 12 份普通预测报告已使用共享等级、8 种基础风格和分类修饰标签，读取模糊未来信号并继承上一期观点；神级与隐藏真值只进入独立开发审计发布；
- 有效客流预测为 v1.2 总量+五客群模型；配置、评分和 Viewer 发布已拆分，配置目录有 Schema，完整预测 JS 已退出；
- 北京是唯一具备完整动态经营闭环的城市；
- 估值仍是实验观察，不是成熟游戏功能。

## 2. 第一优先：统一机场经营界面

下一项明确的产品方向，是把当前三个分散角色整理成一个正式经营主体：

```text
Seed 动态测试中的北京经营总览与事务
  + 有效客流预测 Viewer 的信息与预测
  -> 统一的机场经营模拟
```

目标结构至少包含：

1. **总览**：经营历史、财务、客流容量、服务质量、设施项目、债务融资、合同和商业板块。
2. **预测**：报告等级、历史报告、有效客流预测，以及预测与后来实际结果的对照。
3. **经营事务**：合同、项目和融资操作。
4. **时间与存档**：季度推进、行动日志和当前 Seed 存档。

原“北京机场经营”只读页已经由 `/city-markets` 城市航空市场 Viewer 取代；它负责 47 城筛选和单城市长期市场分析，不再承担北京财务与经营事务，因而不属于上述未来合并范围。

实施原则：

- 先合并展示和导航，不同时修改模型公式；
- 动态测试可以逐步改名为“机场经营模拟”；
- 有效客流预测页面先保留为开发核对入口，统一经营页面稳定后再决定是否移出首页；旧北京只读经营页已经删除；
- 现有正式 URL 先保留兼容；
- 估值不作为保留独立页面的理由，也不在界面合并中顺便重做。

### 开始前必须解决

预测 Viewer 已经分离玩家与审计数据；Seed Explorer 当前响应仍包含完整 `allQuarters`。若统一页面要成为正式游戏界面，仍必须让经营服务端只返回当前季度允许看到的历史和必要摘要，避免浏览器直接拥有经营真实未来。

还需先定义：

- 报告按需加载在统一页面中的缓存与失效规则；
- 独立预测页面的退出条件与正式 URL 兼容期；
- 固定 Seed、浏览器交互和信息可见性验收。

## 3. 第二优先：继续收窄服务端职责

正式服务已归位，但 `airport_sim/server/app.py` 仍同时承担部分路由、运行编排、玩家模拟、序列化及合同/项目/融资规则。

后续可按机械搬移顺序整理为：

```text
routes
services/run_service
services/player_simulation_service
repositories/cache_repository
domain/contracts
domain/projects
domain/financing
serializers
```

每一步要求：

- 不改变公开 URL 和 JSON；
- 固定 Seed API 快照完全一致；
- 新模块纳入缓存指纹；
- 不借移动代码修改玩家规则。

有效客流预测的 data client 与 Renderer 已从页面装配中分离。前端后续只评估 Seed Explorer 剩余的大型交互；当前没有为了拆文件而引入 React/Vue 的必要。

模型公共工具也只按“行为已经证明相同”的小组继续抽取。不同模块的舍入位数、缺失值、编码和字段顺序仍可能具有不同契约，不能为消除重复一次性统一。

## 4. 第三优先：补齐数据协议与发布生命周期

已有关键 API 和 Viewer 分块 Schema，但存档、缓存列表等次要接口还没有专用 Schema，各响应也仍有历史包装差异。

后续工作：

- 为需要独立演化的存档和缓存接口补 Schema；
- 引入命名运行 Profile，在不改旧默认的前提下明确正式、缓存和调试产物；
- 将原子写入逐步扩展到仍会直接覆盖的单层正式输出；
- 为 Viewer release 制定历史保留策略；
- 在剩余内嵌引导脚本处理后评估 CSP；
- 增加 ETag、精细 Cache-Control 和可选 gzip/Brotli；
- 为大体积报告块评估按需压缩、ETag 和精细 Cache-Control，不重新引入整包预测数据。

这些工作必须继续保留“先数据块、后索引/Manifest 指针”的发布顺序。

## 5. 产品与模型的后续方向

以下内容应各自成为独立设计任务，不能混入界面整理：

- 为合同加入合作方、报价选择与谈判过程，而不只是确认建议条款；
- 让项目方案、合同条款和融资条件在确认行动前能够按同一口径测算比较；
- 明确自营商业预算的预测边界，并另行设计免税、奢侈品等商业销售预测；
- 让合同报价基于玩家可见预测，而不是读取隐藏真实未来；
- 完善报告获取成本、质量和预测—实际对照的游戏机制；
- 在北京闭环稳定后，再按[北京样板与新增完整经营城市指南](../reference/Beijing_Template_and_New_City_Guide.md)评估把季度经营扩展到其他城市；
- 重新设计估值的用途、输入和玩家反馈后，才把它升级为正式定价系统。

涉及公式、参数或随机数消费的变化必须升级模型版本，并建立新的固定 Seed 预期，不能以“重构”名义修改现有结果。

更长期的候选方向包括研究所、商业情报中心、市场共识、机场资产交易/并购，以及多人或 AI 对手。它们目前没有实施顺序，也不应提前写入当前架构或界面说明；只有形成独立规则、数据边界和验收标准后才进入开发阶段。

## 6. 明确暂缓：区域与城市并行

全球主链之后的 14 区和城市市场理论上可以并行，但当前不实施。主要原因：

- 固定 Seed 的随机数、浮点和汇总顺序必须完全一致；
- Windows 多进程使用 spawn，会重复导入大模块并传输大列表；
- 12 年短 Run 的进程成本可能超过收益，60 年也缺少普通用户机器的实测；
- 多 worker 会提高内存峰值和跨平台差异。

只有满足以下条件才重新开启：

1. 性能剖析证明模型计算而非 IO、Viewer 或缓存检查是主要瓶颈；
2. 先实验一个清晰边界，不使用嵌套进程池；
3. worker 不直接写共享输出，由父进程固定排序、校验和写盘；
4. Windows/Linux、12/60 年、1/2/4 worker 都有耗时和内存数据；
5. baseline、occurred、probabilistic 的逐行输出与串行版本一致。

## 7. 明确暂缓：玩家行动增量重算

玩家行动后从某季度开始增量重算理论上有收益，但经营账本具有强路径依赖。正确期初状态至少包含现金、资产与折旧、在建工程、贷款、税损、合同周期、项目进度、容量、维护年龄、槽位名称和服务质量。

当前没有版本化季度状态恢复接口，全量重算成本仍可接受，因此继续使用：

- 行动日志指纹复用未变化结果；
- 无新行动时在浏览器复用 `allQuarters`；
- 有新行动时由服务端完整重算。

重新开启增量实现前必须具备：

- 可校验、可迁移的完整季度状态快照；
- 从快照恢复的正式接口；
- 合同、翻新、新建、拆除、重建和各类融资组合回放；
- 全量与增量逐行等价测试；
- 模型或配置升级后废弃旧快照的规则；
- 同季度多动作、修改和删除动作的稳定顺序。

## 8. 每个阶段的共同完成标准

一个阶段只有在以下条件都满足时才算完成：

- Python 3.13 完整测试通过；
- 固定 Seed 数值没有无意变化；
- API、Schema、前端和文档同步；
- Run、缓存、发布和存档边界没有混淆；
- 涉及 UI 时完成五个页面的浏览器验收；
- 兼容入口有明确保留或退出结论；
- 新计划只记录尚未完成事项，不再追加长篇实施流水账。
