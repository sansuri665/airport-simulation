# 文档维护规则

这套规则用于防止项目文档再次变成版本历史、计划草稿和当前说明的混合物。

## 核心原则

1. **正式文档只描述当前事实。** 已经失效的实现、旧目录和完成过程不继续追加在正文中。
2. **一个事实只有一个主要解释位置。** 其它文档用链接引用，不复制整段内容。
3. **代码和机器可检查文件优先。** 文档与代码、配置、Schema 或测试冲突时，应先核实真实实现，再修正文档。
4. **未来事项只进入计划目录。** `Roadmap.md` 维护优先级；只有范围已经明确且由路线图引用时，才建立独立实施计划。不把“以后可能做”写成已经存在的能力。
5. **被取代的文档直接删除。** Git 已经保存历史，不再建立堆满旧稿的归档目录。

`releases/` 是唯一例外：这里只保存已经形成 Git 阶段边界的正式交接说明，用来解释对应标签包含什么、怎样验收和如何恢复。发布说明记录当时事实，不作为当前使用指南，也不因后续 API 或目录变化而回写；当前事实仍以专题文档和代码为准。

## 信息应该放在哪里

| 信息类型 | 主要位置 |
| --- | --- |
| 项目是什么、玩家能做什么 | `product/` |
| 如何启动和使用界面 | `getting_started/` |
| 前后端、目录和数据关系 | `architecture/` |
| 模型原理和层级关系 | `models/` |
| 参数、API、字段和术语 | `reference/` |
| 测试、修改约束和排错 | `development/` |
| 尚未实施的工作 | `plans/Roadmap.md` 及其明确引用的实施计划 |

## 每篇专题文档的建议结构

模型和系统专题通常按以下顺序编写：

1. 这部分解决什么问题；
2. 普通读者应该怎样理解；
3. 输入是什么；
4. 经过哪些处理；
5. 输出给谁；
6. 与其它模块是什么关系；
7. 真实代码、配置或 Schema 在哪里；
8. 当前明确限制是什么。

不要求为了套模板而保留空章节，但同类文档应使用相近顺序。

## 不再使用的写法

正式文档中避免以下内容：

- 按日期不断追加的“本次完成”“下一阶段”“后来又修改”；
- 同一功能从 v0.1 到 v0.5 的完整演变过程；
- 已经完成但仍保留为待办的复选框；
- 大段复制代码，而不解释输入、输出和约束；
- 同一参数在多篇文档中各写一个不同数值；
- 把设计设想写成当前可运行功能；
- 为了保留旧链接而留下内容已经无效的空壳文档。

历史提交说明、旧设计和删除内容可以通过 Git 查看；真正影响当前维护决策的限制应直接写成当前规则，而不是依赖读者还原历史。

## 路径和数值引用

- 路径使用仓库根目录相对路径，例如 `airport_sim/server/app.py`。
- 浏览器地址写成稳定 HTTP 路由，不把 `web/pages/` 物理位置当成 URL。
- 参数应说明单位、口径和配置来源；没有固定全局值时不要写成唯一常数。
- 输出示例只用于解释结构，不能把某次 Seed 的结果写成永久事实。
- 文档内链接优先使用相对链接，并在提交前检查目标文件存在。

## 修改功能时的文档检查

修改代码或配置后，至少检查：

- 项目入口或命令是否变化；
- 页面 URL、API 或 Schema 是否变化；
- 模型输入、输出、单位或计算顺序是否变化；
- 配置文件和参数来源是否变化；
- 当前能力或限制是否变化；
- 路线图中的事项是否已经实现或不再需要。

只更新受到真实变化影响的主要文档，避免把同一变更复制到所有页面。

## 删除或合并文档

删除前确认旧文档中的当前有效事实已经进入新的主要文档，并检查全项目没有继续引用旧路径。完成后直接删除旧文件；除非它是仍有现实用途的审计或决策记录，否则不迁入 `archive/`。

文档重写或大规模合并完成后，应执行：

1. Markdown 内部链接检查；
2. 路径存在性抽查；
3. 命令 `--help` 或只读运行检查；
4. 旧文档名和旧目录引用搜索；
5. `git diff --check`。
