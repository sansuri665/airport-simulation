# 网页模型 Handoff 规范

## 用途

网页强模型适合处理范围明确但推理或编码难度较高的单个问题；它的主要限制是看不到完整本地工作区、运行服务、Git 状态和真实测试环境。

本项目用根目录 `handoff/` 作为人工传输通道：本地代理负责选择上下文、建立交接包、应用返回修改和真实验收；网页版模型负责在明确规格内分析和修改；用户只负责上传和下载。Handoff 不改变任何代码权威关系。

```text
docs/plans/ 中的目标与验收
          ↓
本地选择足够且聚焦的上下文
          ↓
handoff/outbox/<task-id>.zip
          ↓  用户上传
网页版模型修改并返回
          ↓  用户下载
handoff/inbox/<task-id>/
          ↓
本地审查、选择性应用、真实测试
          ↓
原代码目录与正式文档
```

## 权威边界

| 内容 | 权威位置 |
| --- | --- |
| 未来目标、范围和完成条件 | `docs/plans/` |
| 当前实现 | 原始代码、配置和 Schema 目录 |
| 当前正式说明 | `docs/models/`、`docs/reference/` 等专题文档 |
| 测试结果 | 本地 Python 3.13、Node/浏览器和 CI 的真实输出 |
| 网页往返文件 | `handoff/outbox/` 与 `handoff/inbox/`，仅作临时运输 |

网页返回的代码、报告和“测试通过”声明都不是当前事实。只有修改被本地有选择地应用、通过相应验收并进入正常 Git 阶段后，才成为项目状态。

## 什么时候使用

适合：

- 单个复杂算法或重构子 Goal；
- 已经知道主要文件、约束和测试，但希望获得另一种强模型实现；
- 能用边界明确的源码切片和只读上下文完整解释的问题；
- 本地代理准备在返回后重新审查和运行测试的问题。

不适合：

- “把整个项目优化一下”一类没有边界的请求；
- 必须实时操作浏览器、服务、数据库、GitHub 或大体积 Run 的任务；
- 需要读取整个 `output/`、`saves/` 或多 GB 数据才能判断的问题；
- 需要在多个未冻结 Goal 之间反复联调的问题；
- 包含凭证、私人数据或不能上传第三方服务的内容。

一个交接包只对应一个子 Goal。即使模型价格低，也不把多个高风险数值 Goal 合并发送。

## 资源与 Token 策略

当本地强模型额度不足以同时推进多个项目时，网页版 Pro 可以承担“规格已经冻结、编码和局部实验工作量较大”的执行阶段。本地模型保留四项权威职责：定义 Goal、组织上下文、做对抗性审查、在完整仓库验收。网页版模型不是廉价替代品，也不是最终裁判，而是可并行利用的强执行资源。

是否节省 Token 按完整闭环计算：

```text
本地编写规格与打包
  + 网页模型实现
  + 本地审查、修正和测试
  + 因上下文不足造成的返工
```

如果第一次交接包能够直接运行目标测试、理解调用链并看到关键反例，通常比本地模型独立完成全部编码更省额度。反之，过度追求“小压缩包”会把成本转化为多轮上传、缺依赖、错误假设和本地重做。默认策略因此是：**一个 Goal、一次尽量完整的首包、一次本地强验收**；只有新增证据确实改变设计时才进行第二轮网页往返。

对于数值模型、跨层字段链和发布生命周期等高风险任务，至少保留一项本地盲验收：例如未放入包内的新 Seed、跨进程组合、真实浏览器流程或针对候选算法的反例。包内测试用于帮助网页模型实现，包外验收用于防止只对已知样例过拟合。

## 目录约定

```text
handoff/
  README.md
  outbox/
    YYYYMMDD-<short-task>.zip
  inbox/
    YYYYMMDD-<short-task>/
  work/
```

- `README.md` 进入 Git，解释目录角色；
- `outbox/`、`inbox/`、`work/` 被 `.gitignore` 排除；
- 打包和解压优先使用系统临时目录，只有最终待传输文件进入 inbox/outbox；
- 不在根目录留下 `_audit_*`、`_verify_*`、聊天日志或完整代码副本；
- 任务被本地接受并形成 Git 阶段后，inbox/outbox 文件即可删除；Git 不承担网页往返归档职责。

## 发出包的最低结构

每个压缩包至少包含：

```text
HANDOFF_INSTRUCTIONS.md
docs/plans/<relevant-plan>.md
<editable source files in original relative paths>
<relevant tests in original relative paths>
<minimal read-only context in original relative paths>
```

复杂任务建议再加入：

```text
CONTEXT_MAP.md                 # 模块关系、入口和文件角色
BASELINE_RESULTS.md            # 真实失败命令、摘要和已知反例
examples/                      # 小型输入、期望输出、Manifest/API 样例
FILE_MANIFEST.sha256           # 包内文件清单与校验和
```

这些文件是传输辅助，不自动进入正式源码。若 `HANDOFF_INSTRUCTIONS.md` 已经清楚覆盖相同内容，可以合并而不机械增加文件。

`HANDOFF_INSTRUCTIONS.md` 必须写明：

1. 唯一任务和明确不做什么；
2. 当前 Git 基线和工作区是否 dirty；
3. 当前可复现失败、Seed、测试或截图；
4. 必要的业务背景、字段语义和一个正例、一个反例；
5. 可以修改的文件；
6. 只能参考、不得改经济系数或公共契约的文件；
7. 禁止捷径，例如放宽阈值、刷新失败 baseline、删除测试；
8. 要求返回的相对路径、补丁和报告格式；
9. 包内能够运行的测试，以及只能回到完整本地仓库后运行的测试；
10. 不提交、不打 Tag、不推送的边界。

包内保留原仓库相对路径，方便返回后逐文件比较。只读与可编辑文件可以共用原目录结构，但必须在说明中逐项分类；不要为方便打包改写 import 或制造第二套项目布局。

## 足够上下文原则

Handoff 追求的是“任务切片语义完整”，不是文件数最少。本地打包者按以下顺序选择内容：

1. 目标计划章节；
2. 全部直接待修改实现，而不是只截取当前怀疑的函数；
3. 直接测试、测试辅助、失败 fixture 和固定样例；
4. 让目标测试能够导入和运行的完整调用者、被调用者与包结构；
5. 配置、Schema、版本记录和字段契约；
6. 一个正常样例、一个已知失败样例，以及容易误判的反例；
7. 只有理解公式或业务口径确实需要时，才加入更远的只读背景。

源码、配置、Schema、测试和小型 fixture 可以比旧交接包更完整。只要仍是单一 Goal、没有敏感信息且不包含生成物，几十到上百个文本文件通常比缺失真实导入链更合适。不要为满足任意文件数或压缩大小而删掉测试辅助、公共序列化器、版本文件或示例 Manifest。上传平台限制才是包大小的硬边界；达到限制时优先删除重复文档和可重建资产，而不是关键执行上下文。

可按任务复杂度参考以下档位，但不作为硬配额：

| 档位 | 适用任务 | 推荐内容 |
| --- | --- | --- |
| 小 | 单文件缺陷、明确机械修改 | 直接实现、对应测试、最小契约 |
| 中 | 单一子系统重构或 API 字段链 | 完整子系统、调用链、配置/Schema、相关测试与样例 |
| 大 | 数值求解、跨层集成、发布生命周期 | 可独立运行的源码切片、完整测试辅助、多个代表 Seed、失败报告、正反例和版本契约 |

下一次宏观或利率类网页交接默认按“大”档准备：应尽量让网页版在解压目录中直接执行定向测试和审计脚本，不再依赖大量临时 import 桩。若完整仓库中的某些模块体积不大且是导入链必要部分，可以一并加入；仍然禁止加入 Run、Release 和玩家存档。

不要上传：

- `.git/` 和 Git 凭证；
- `.env`、API Key、访问令牌、Cookie、用户配置；
- `output/`、`saves/`、Viewer Release、Run 和缓存；
- 与目标无关的前端、图片、文档或依赖；
- 能从少量摘要表达的巨大日志；
- 另一个尚未开始的子 Goal 全部代码。

打包前检查归档条目和常见密钥模式。出现疑似凭证时停止，不依赖“模型不会使用”作为安全理由。

## 给网页版模型的要求

入口提示词保持短小，让包内说明成为唯一细节来源：

```text
解压后先完整阅读 HANDOFF_INSTRUCTIONS.md，严格执行其中唯一子 Goal。
请返回保持原相对路径的修改文件或 unified diff，以及 CHANGE_REPORT.md。
不要声称未在完整仓库真实执行的测试已经通过。
```

网页版模型应返回：

- 同相对路径的完整修改文件，或可应用 unified diff；
- `CHANGE_REPORT.md`，说明根因、设计选择、修改文件、测试建议和剩余风险；
- 若它没有完整运行环境，明确写“未执行测试”；
- 不返回整个无关项目，不生成 Git 提交或发布说明。

## 接收与应用

网页返回物不得直接覆盖真实工作区。接收方按顺序处理：

1. 放入 `handoff/inbox/<task-id>/`；
2. 检查压缩包是否包含绝对路径、`..` 路径穿越、额外可执行文件、`.git/`、凭证或范围外文件；
3. 解压到系统临时目录或 `handoff/work/`；
4. 对照发出清单和 `CHANGE_REPORT.md` 查看新增、修改、删除文件；
5. 与当前 dirty 工作区逐文件比较，确认网页修改没有覆盖用户随后产生的变化；
6. 使用有意的补丁或逐文件编辑应用，不进行整目录覆盖；
7. 先运行定向测试，再按[测试分层规则](Testing_and_Safe_Changes.md)运行 `quick + 受影响领域`、计划规定的多 Seed 和必要浏览器验收；只有 GitHub 大版本或高风险基础例外才运行 `full`；
8. 测试失败时保留原始证据，判断是修复、部分采纳还是拒绝，不更新失败 baseline；
9. 验收完成后按正常本地 Git 机制形成阶段记录。

本地验收不能只重跑网页模型新增的测试。至少增加一次“审查者反例”：检查实现是否通过缩小步长、裁剪输出、刷新摘要或只满足已知 Seed 来制造绿灯。数值求解任务应优先验证残差或不变量，不能只验证算法自己定义的停止信号。

如果返回物缺少关键文件或依赖旧快照，优先让本地代理补小范围修改；只有设计本身需要重新推理时才生成新的 outbox 包。不要把同一个旧包反复上传并让上下文逐轮漂移。

## Handoff 中的文档维护强度

网页模型完成的是候选实现，不负责为每个本地小版本重写整个项目文档体系：

- 未上 GitHub 的本地小版本，优先维护代码、测试、Schema、必要的专题契约，以及当前临时路线文档中的状态、实测结果和未决风险；
- 没有改变用户入口、公共 API、数据字段或模型口径时，不要求同步重写根 README、所有专题文档、Release 说明和历史版本记录；
- Handoff 候选尚未本地验收时，只更新 `CHANGE_REPORT.md` 或临时路线，不把候选行为写成正式事实；
- 本地验收通过后，只更新真正受到影响的主要文档；阶段尚未推送 GitHub时，不建立发布说明；
- 形成 GitHub 大版本、正式 Tag 或外部可见契约变化时，再完成正式专题文档、版本记录、Release 说明和恢复边界。

临时路线文档是例外：只要一个阶段 Goal 仍依赖它，就必须维护“已完成、未完成、真实测试、版本和提交状态”，避免下一位执行者按照过期失败基线重复工作。整个路线完成并把当前事实提炼到正式文档后，再按文档规则删除临时路线，而不是长期保留流水账。

## 成本记录

每个 Handoff 的最终本地验收摘要建议记录：

- 网页模型和模式；
- 发出包文件数与压缩大小；
- 网页修改被完整、部分或拒绝采纳；
- 网页端真实可见的 Token/额度或调用次数；
- 本地审查 Token、墙钟时间和测试时间；
- 与本地模型直接实现相比，是否减少返工。

无法获得精确 Token 时写“不可获得”，不根据文件行数伪造精确数值。是否降本以“最终通过验收的有效修改”为准，不以生成代码量为准。

## 清理和项目整洁

- `handoff/` 不建立长期任务历史；正式决策回到计划、专题文档、测试和 Git；
- 被采纳的 `CHANGE_REPORT.md` 只在确有持续维护价值时提炼到正式文档，不原样归档；
- 未采纳返回物可以在结论记录后删除；
- 返回修改一旦完成白名单审查、合入项目并通过本地验收，发出 ZIP、返回 ZIP、解压副本和临时 staging 应直接删除，不再另建 Handoff 历史归档；需要长期保留的只有 Git 变更、正式测试和提炼后的结论；
- 当前仍待上传、待审查或需要用来复现未解决问题的包可以暂留；删除前必须按任务 ID 精确确认目标，不能批量清空其他正在进行的 Handoff；
- inbox/outbox 不参与 Release、Viewer、缓存或存档保留策略；
- 文档链接只引用 `handoff/README.md` 和本规范，不引用某个会被删除的压缩包。

这一机制的目标是给网页版模型提供足够而有限的上下文，同时保持 Airport 的源码、文档、Git 和运行数据边界不变。
